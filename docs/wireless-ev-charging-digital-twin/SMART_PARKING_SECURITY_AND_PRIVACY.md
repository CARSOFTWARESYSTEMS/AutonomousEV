# Smart Parking — security and privacy

This document covers what the public twin does and does not handle, the threat model for a physical deployment, the controls the simulation demonstrates, and the privacy design for plate and image data.

## 1. The public application

| Property | How it holds |
|---|---|
| Synthetic data only | Vehicles, plates, RFID tags, QR tokens, sessions, payments and telemetry are generated by seeded models. The plates use markers that cannot be issued: state code ZZ (IN), a leading 0 (US) and the test character 测 (CN) |
| No personal data | No account, plate, image, location or payment detail of any person is collected or processed by Environment 01 |
| No secrets in the browser | There are none to leak. The message integrity tag is the simulator's own FNV-1a check with a public key string, used to demonstrate tampering detection. It is not cryptography and protects nothing real |
| No real payment | Payment providers are named adapters (UPI-class, card-network, mobile-wallet) marked *simulated*. The driver panel collects no card number, UPI handle or credential |
| No physical actuator | No command leaves the browser. Operator actions act only on the in-browser simulation, through the same role, expiry, replay and interlock checks a device controller would apply |
| Honest data modes | Values are SIMULATED, or RECORDED during replay. LIVE is reserved for authorised hardware, and none is connected. The hardware operating modes are listed as blocked |
| Exports stay with the visitor | Study results and recordings download as JSON files to the visitor's own device, labelled with their data mode. Nothing is uploaded |
| No confidential governance | Programme governance and IP records are kept out of the application. SMART_PARKING_GOVERNANCE_TEMPLATE.md is a blank template |

### Roles in the operator panel

The panel acts as **Viewer** (read-only), **Operator** or **Supervisor**. Permissions follow least privilege (`telemetry.ts · PERMISSIONS`):

- A viewer issues nothing.
- An operator can block or unblock a bay, approve or refuse an identity, acknowledge an alarm, set lighting and fans, open or close a barrier, and stop charging.
- Only a supervisor may force-release a bay.

Every attempt is written to the audit log with its actor, role, action, target, result and reason, whether it is accepted or rejected (SP-B08). The browser check *a viewer cannot override* verifies the viewer case.

## 2. Threat model (physical deployment)

| Threat | Example | Control in the design | Demonstrated in the simulation |
|---|---|---|---|
| Device spoofing | A rogue node publishes "bay vacant" | Per-device X.509 client certificates; broker refuses non-TLS connections; ACL limits each device to its own topics | TLS-required connect; ACL refusal logged with reason |
| Message tampering | A modified occupancy message | TLS in transit; schema validation; integrity check | Integrity-tag mismatch → INVALID |
| Replay | An old "open barrier" command resent | Command ids, expiry and clock-skew checks at the controller | Replay, expiry and skew refusals (SP-B08) |
| Duplicate or reordered data | Network duplicates an occupancy event | Idempotent ingestion by event id; per-device, sensor and topic sequence | SP-B19; out-of-order messages kept but never regress state |
| Stale data | A node stops, and its last value looks current | Freshness limit; heartbeats; last will | STALE marking (SP-B20); stale-data and message-pattern anomalies |
| Flooding | A node or attacker floods the broker | Per-device rate limit; broker limits; segregated device network | Token bucket, 20 messages/s per device |
| Unauthorised command | A driver account tries to open a barrier | Role-based permissions; commands only via the gateway | Role refusal; viewer issues nothing |
| Unsafe actuation | A valid command to close the barrier on a car | Local interlock in the barrier controller, independent of the network | SP-B07: refuses and reverses |
| Loss of gateway or cloud | Power failure, outage | Local safety controllers; exits open for egress; charging stops; store and forward | SP-B09, SP-B24 |
| Remote compromise of the twin | The twin used to command the facility | The twin is read-only toward hardware; no inbound connection to the site | `connected-read-only` refuses every command |
| Plate misidentification | A wrong read grants access | High accept threshold; uncertain reads never authorise; RFID, QR or operator fallback | SP-B02 |
| Tailgating | A second car follows on one authorisation | Clear-zone sensor; operator referral | SP-B25 |
| Insider misuse | An operator looks up a person's movements | Purpose limitation; access logging; minimal retention; keyed plate hashes | Audit log of every command (look-ups are not modelled) |
| Supply-chain or firmware | A modified node image | Signed OTA images; A/B partitions with rollback; asset register of firmware versions | Not modelled |

## 3. Privacy design for a deployment

Number plates, and images that contain them, are personal data in many jurisdictions. A deployment must follow the law of its jurisdiction, with qualified advice. The design below is a starting point, not a compliance claim.

1. **Purpose limitation:** plates are used only for access, allocation, billing and dispute resolution. They are never used for tracking or profiling.
2. **Minimisation:**
   - Recognition runs at the edge.
   - Images are discarded after the read, unless they belong to a declared evaluation dataset collected with consent.
   - No face processing of any kind.
3. **Pseudonymisation:** the session keeps a keyed hash of the plate (HMAC with a site key held on the gateway), which is enough for matching. Plain text is kept only for the access list and open disputes.
4. **Retention:** configured per region (SMART_PARKING_INTERNATIONALIZATION.md §3), with automatic deletion.
5. **Access:** least-privilege roles, every look-up logged, and access reviewed periodically.
6. **Transparency:** signage at the entry and a privacy notice. Drivers can use RFID or QR instead of plate recognition, where the operator offers that.
7. **Assessment:** a data-protection impact assessment before deployment.
8. **Research data:** only aggregated or pseudonymised exports. Evaluation datasets use synthetic plates on the POC's miniature vehicles.

## 4. Operational security for the POC

- Separate device network, with no inbound path from the internet. Any remote viewing is outbound-initiated and read-only.
- Unique credentials per device, provisioned at commissioning and revoked at replacement (SMART_PARKING_HARDWARE_PLAN.md §4).
- Firmware and gateway updates are signed. The gateway runs only the services it needs, with host firewall rules.
- Secrets never go into the repository, the twin's source or its generated documents.
- Logs exclude secrets and plain plate text.

## 5. What remains to be done before any physical deployment

- An independent security assessment of the gateway, broker configuration and firmware.
- A real cryptographic command-signing scheme (asymmetric, per issuer) to replace the simulator's integrity tag.
- The data-protection assessment and retention configuration for the deployment jurisdiction.
- Payment through an approved provider integration, with the provider holding all payment credentials.
